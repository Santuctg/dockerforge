# DockerForge security review — 2026-10-25

**Scope:** `Santuctg/dockerforge` at commit `0e9304d` (pyproject still declared `0.7.0` although the v0.8.0/v0.9.0 feature sets were present), plus the v0.9.0 hardening patch set in this working tree.
**Review type:** Internal, source-level review and remediation. Not an independent penetration test or audit.
**Reviewer:** OpenCode agent session, 2026-10-25.
**Verification:** 230 pytest tests pass; ShellCheck exits clean on all installer and script files.

---

## 1. Executive summary

DockerForge is a single-host Docker management panel. Its security posture is dominated by one design fact: the web service talks to `/var/run/docker.sock` and the service user is in the `docker` group, which is equivalent to host root. Every other control is therefore about preventing an attacker from *reaching* that capability, not about containing it.

The original code had a good foundation — parameterised SQL, Argon2id password hashing, session-bound CSRF, role checks on every mutating route, redacted Docker errors, no shell invocation — but it shipped three issues that materially weakened it:

1. **No Content-Security-Policy and inline event handlers everywhere** (script injection would become host compromise).
2. **A CSRF rotation bug that made a second browser tab break the first one**, which pushes users toward disabling protections or retrying blindly.
3. **A firewall default that published `9443/tcp` to the internet**, contradicting the documented "restrict to VPN" guidance.

All three are fixed in this patch set, together with a set of medium/low defects found during the review. The remaining risks are mostly architectural and are listed in §6.

**Residual risk rating: HIGH, by design.** Any bug that yields script execution, an authenticated admin session, or Docker API access yields host root. The panel should stay on a private network and be treated as a root console.

## 2. Architecture and trust boundaries

```
browser ──HTTPS(9443)──> uvicorn/FastAPI ──unix socket──> dockerd ──> containers
                          │
                          ├─ SQLite: users, sessions, audit, backups
                          └─ systemd metrics collector (same service user)
```

| Boundary | Trust |
|---|---|
| Internet/LAN → 9443 | Untrusted. TLS only, session cookie, CSRF, login rate limit. |
| Panel → Docker socket | Fully trusted. Any authenticated admin action is host-root capable. |
| Web service → `/etc/dockerforge` | Read-only for the service; secrets are `root:dockerforge 0640`. |
| Backup timers | Run as **root**; the web UI can only list archive metadata. |
| Reverse proxy → panel | Trusted only when listed in `DOCKERFORGE_TRUSTED_PROXIES`. |

Roles: `viewer` (read), `operator` (+ exec/logs/ack), `admin` (+ container edit/create, stacks, alerts), `super_admin` (+ users). Viewer/operator never receive container environment values; logs and exec require operator, and exec on a high-risk container requires admin.

## 3. Findings and remediation

Severity uses a qualitative scale (Critical/High/Medium/Low/Info). "Fixed" means code and regression tests are in this tree.

### DF-01 — CSP and inline handlers (Critical)

**Before:** `home()` returned the SPA without a script policy; `ui.py` used 26 inline handler attributes. The UI consistently writes untrusted data with `textContent`, so this was not directly exploitable in the reviewed code, but any future `innerHTML` mistake or third-party injection would have executed script in an origin that can start privileged containers.

**Fix:**
- `home()` generates a per-response nonce and sends
  `default-src 'self'; script-src 'nonce-…'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'`.
- All static inline handlers were replaced with `data-action` attributes and three delegated listeners (`click`, `change`, `input`) in one nonce-bearing script. No `onclick="`/`onchange="`/`oninput="` attributes remain (regression-tested).
- Non-panel responses get `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`.
- Added `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
- Remaining `innerHTML` use is a constant first-run/login form with no interpolation; dynamic rows continue to use `textContent`.
- `style-src 'unsafe-inline'` is retained because the single-file UI uses a `<style>` block and inline style tweaks; styles cannot execute script.

**Why not `script-src 'self'`:** the SPA is an inline script. A nonce keeps it working while still blocking injected inline scripts and event-handler attributes.

### DF-02 — Multi-tab CSRF (High)

**Before:** one `sessions.csrf_hash` per session, replaced on every `/auth/csrf` call. Tabs share cookies, so tab B's fetch broke tab A's next write.

**Fix:**
- New `session_csrf(id_hash, csrf_hash, created_at)` table keeps at most `CSRF_TOKENS_PER_SESSION = 8` recent tokens per session. Tokens are stored hashed, cascade-delete with the session, and are pruned on insert.
- `require_csrf` now validates the **header token** against the session (current hash or a recent stored hash). The CSRF cookie is still required as a presence/defence-in-depth signal, but a cookie/header mismatch caused by another tab no longer rejects a valid token.
- Rationale: a cross-origin attacker cannot read the token (HttpOnly cookie, SameSite=Lax, no CORS) and cannot set a custom header on a form post, so the session-bound header token is the security boundary. Rotating the cookie no longer invalidates open tabs.
- Pre-login `/auth/csrf` now reuses the existing cookie value for unauthenticated clients, so two login tabs share one double-submit token. Login itself still requires `cookie == header` (no session exists yet).
- Login and setup still create a fresh session/token; logout deletes the session (cascade removes stored tokens).

Regression tests cover: old token accepted after another tab refreshes the cookie, unknown token rejected, oldest token evicted after 8 refreshes, pre-auth token reuse across tabs.

### DF-03 — Firewall default (High)

**Before:** `step_firewall` unconditionally ran `ufw allow 9443/tcp` / `firewall-cmd --add-port=9443/tcp`.

**Fix:** new `--allow-public` flag. Default behaviour:
- No `--domain`: no firewall change; prints that `9443/tcp` is left closed and recommends VPN/tunnel/`--allow-public`.
- `--domain` with HTTP-01: opens **only** port 80 for the ACME challenge, panel port stays closed.
- `--allow-public`: opens 9443 (plus 80 when HTTP-01 needs it).
- `--no-firewall` still skips everything.

The panel still binds `0.0.0.0:9443`; operators must rely on firewall/network policy. README and `install.sh --help` document this.

### DF-04 — Client IP behind a proxy (High)

**Fix:** `DOCKERFORGE_TRUSTED_PROXIES` accepts comma-separated IPs/CIDRs. `client_ip()`:
1. Uses the TCP peer unless it belongs to a trusted network.
2. Parses `X-Forwarded-For` right-to-left and returns the first hop that is **not** trusted.
3. Ignores malformed entries and falls back to the peer.

This makes the spoofable left-hand prefix irrelevant: a client can prepend anything, but the right-most untrusted hop is the address the nearest trusted proxy actually saw. Invalid configuration entries are ignored rather than crashing. Used by both login rate limiting and `audit()`.

### DF-05 — Backup Center permissions (Medium)

`data-backup.json` is now installed `0640 root:dockerforge` (and `chown`/`chmod` is re-applied on upgrade), so the service can read the safe summary. The UI still never returns SMTP/Cloudflare secrets or archive contents.

### DF-06 — Audit retention (Medium)

`prune_audit()` deletes rows older than 180 days and caps the table at 200,000 rows (oldest first). It runs at startup and every 200 audit writes, guarded by a lock. The `idx_audit_ts` index remains in place. Retention values are module constants and can be tuned without a schema change. Tested with an explicit clock.

### DF-07 — Upgrade path (Medium)

- Version read from `pyproject.toml` with `sed`; missing version is fatal.
- Downgrades are refused using `sort -V`; re-running the same version is allowed.
- Current version is read from the installed `$APP/pyproject.toml`.
- Dependencies from the staged `pyproject.toml` are installed into the existing venv with `backend_requirements` + `pip install -r` **before** the code swap, inside the rollback trap.
- Staging directory renamed to `.staging-*`.
- `data-backup.json` permissions fixed during upgrade as well.
- User-facing text no longer mentions internal task numbers or a hardcoded release.

### DF-08 — Port validation consistency (Low)

`normalize_host_ip()` accepts IPv4, IPv6, `''` and `*` (both normalised to `''` = all interfaces). `is_public_host_ip()` treats only `127.0.0.1` and `::1` as non-public, so IPv6 loopback and wildcards now require `acknowledge_public_ports` like IPv4 did. Duplicate wildcard spellings (`''`, `0.0.0.0`) are rejected as duplicates. `validate_port_availability` parses addresses and treats `''`, `*`, `0.0.0.0`, `::` as wildcards on either side.

### DF-09 — Collector (Low)

`collect_once(..., running=...)` accepts a prefetched inventory. `main()` now fetches `list_containers(all=True)` once per cycle and reuses it for sampling, stopped/paused counts and alert-rule reconciliation. `inventory_counts()` counts only `exited`/`dead`/`created` as stopped; `paused` is reported separately and does not fire the stopped alert or the rule-based stopped alert.

### DF-10 — Host stats (Low)

`_mem()` and `_net()` tolerate missing/unreadable procfs and malformed lines. When procfs is absent, memory total/available come from `os.sysconf('SC_PHYS_PAGES'/'SC_AVPHYS_PAGES')`. This also makes the existing integration test meaningful on macOS.

## 4. Controls verified as sound

- **SQL:** every query uses parameters; no string-built SQL with user input.
- **Passwords:** Argon2id via `argon2-cffi` with library defaults; 12-character minimum; hashes never returned by any endpoint.
- **Sessions:** 48-byte URL-safe token, stored as SHA-256; `HttpOnly; Secure; SameSite=Lax`; 30-minute idle timeout and 24-hour absolute expiry; login issues a new token (no fixation); role change/password reset/delete revokes the target's sessions.
- **CSRF:** session-bound token on every mutating route, including admin user management; login double-submit; SameSite adds a second layer.
- **Rate limiting:** 5 failures per username and 30 per client IP per 300 s; state is pruned and capped at 10,000 keys with a "fewest recent failures" eviction policy so a username flood cannot clear a real lockout.
- **RBAC:** consistent dependency checks; viewer cannot read logs or env; operator exec on bind-mounted/privileged/host-network containers is escalated to admin.
- **Docker adapter:** Unix socket only; path must be absolute and NUL-free; Docker error bodies are not reflected to clients (they can contain secrets); container/network IDs are validated before use.
- **Compose/exec:** no host shell; fixed `docker` CLI with controlled environment; bounded argv count; bounded log bytes.
- **Backups:** tar traversal/symlink/duplicate-entry checks, checksum verification, staging before restore, mandatory pre-restore checkpoint and explicit downtime confirmation; archive operations are CLI-only, not web-triggered.
- **Installer:** root-only execution, OS allowlist, TLS keys `0640 root:dockerforge`, env file `0640 root:dockerforge`, Cloudflare token `0600`, setup token compared with `secrets.compare_digest`, safe re-run preserving data, rollback on failure.
- **systemd:** `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `UMask=0027`, narrow `ReadWritePaths`.

## 6. Residual risks and recommendations

Ordered by value. Items 1–3 are architectural and should be explicit in any deployment approval.

1. **Docker socket = host root (accepted).** Admin, and to a large extent operator, can mount `/`, use `--privileged`, or exec into a privileged container. Do not grant operator to users who are not trusted with root. Consider a rootless/daemonless backend or a brokered API with per-action policy for higher-assurance deployments.
2. **Coarse role model.** Operator can exec in any non-high-risk container; a container with a sensitive mounted secret is not automatically "high risk" unless it has bind mounts/host namespaces/capabilities. Add explicit per-container sensitivity labels and require admin for those.
3. **No MFA/SSO.** A stolen password plus a valid CSRF flow is enough. Add TOTP/WebAuthn for admin/super_admin, and optionally OIDC. Password policy is length-only; add breached-password checks.
4. **No application-level source allowlist.** Firewall/VPN is the only network control; if 9443 is exposed, there is no `/24` allowlist or client-certificate requirement. Add optional mTLS or an IP allowlist in front of the panel.
5. **Audit integrity.** Audit is append-only by convention, stored in a database writable by the service user. A compromised service can edit it. Ship audit events to a remote syslog/HTTP sink and/or sign batches; keep the DB on a filesystem the service cannot rewrite outside normal operation.
6. **Dependency supply chain.** Replace major-range pins with a lock file / constraints file and `pip install --require-hashes`; add Dependabot/Renovate and an SBOM. The current install trusts PyPI at install/upgrade time.
7. **TLS defaults.** Without `--domain`, a 10-year self-signed certificate is generated. Prefer a short-lived self-signed cert and document pinning; add `includeSubDomains`/`preload` only when the deployment owns the whole domain. Consider automated renewal monitoring and certificate-expiry alerts.
8. **Setup token lifetime.** Remove `DOCKERFORGE_SETUP_TOKEN` from the env file after first-run setup (manual or via a small root-owned helper), so a future DB reset cannot be re-bootstrapped with an old token.
9. **Backup jobs run as root.** `dockerforge-backup` and `dockerforge-data-backup` are root oneshots. Consider a dedicated backup user with narrowly scoped sudo/ACLs, and encrypt archives before they leave the host.
10. **No global request-size/time limits.** Compose YAML, environment maps and exec argv are bounded by field limits, but there is no per-request body cap or API-wide rate limit. Add a reverse-proxy body limit (for example 2 MB) and a generic per-IP API rate limit.
11. **SMTP header values come from root-owned env.** A newline in `DOCKERFORGE_ALERT_SMTP_FROM/TO` could inject headers into the alert message. Validate them at startup (single address, no CR/LF).
12. **`DELETE` with a body.** Move the image-delete confirmation to a path/query parameter or a `POST .../delete` action for proxy compatibility.
13. **UI test brittleness.** Many UI tests assert substrings of one large HTML string. The new `data-action` contract is tested, but consider DOM-level tests (Playwright) for login, container create/edit and CSRF flows.
14. **External validation.** This review is source-level only. Before production, commission an independent test that covers authenticated DAST, container escape scenarios, backup/restore drills and TLS configuration.

## 8. Conclusion

The patch set closes the three issues that most directly threatened the host (script injection exposure, CSRF usability failure, public firewall default) and a set of correctness/availability defects around upgrades, backups, ports, the collector and host stats. The security model is still "authenticated users are root-equivalent"; that is acceptable only for a private, well-monitored deployment. Track the residual items in §6 before exposing the panel beyond a trusted network.
